Authentic source API

An interface that lets a qualified trust service provider (QTSP) verify or retrieve company data held by the Brønnøysund Register Centre before it issues an attestation such as the EUCC. It implements the Authentic Source Interface of ETSI TS 119 478 (HTTP variant) on top of the Central Coordinating Register for Legal Entities (Enhetsregisteret).

Draft. Clients authenticate with a static API key and pass the subject in a header. A conformant OAuth 2.0 setup, with the subject in the access token, is planned.

Overview

Specification
ETSI TS 119 478 V1.1.1, clause 6.1 (HTTP variant): Verify (I2) and Retrieve (I3)
Attributes
EU Company Certificate (EUCC) attributes, identified by terms of the European Business Wallet Vocabulary (EBWV v0.1)
Format
JSON, validated against the normative ETSI schemas. Errors as application/problem+json (RFC 9457), except 401, which has no body
Base URL
https://auth-source-api.app-ppe.brreg.no/api/0.2 in the test environment (PPE). 0.2 is the API version, filled into the basePath server variable of the ETSI OpenAPI.
Swagger
Swagger UI at https://auth-source-api.app-ppe.brreg.no/api/swagger and the OpenAPI document at https://auth-source-api.app-ppe.brreg.no/api/api-docs. Reachable only once your IP addresses are opened in the firewall.
Audit
Each call is logged with client, subject, attribute identifiers and results, but without attribute values

Onboarding

The API is for qualified trust service providers (QTSPs) taking part in WE BUILD. It is not open to the public: access needs both a firewall opening and an API token that the Brønnøysund Register Centre creates for each QTSP.

  1. Request access. Contact the Brønnøysund Register Centre’s resources in WE BUILD. The request must come from a QTSP participating in WE BUILD. State the organisation, a technical contact, and whether you need verify, retrieve or both.
  2. Firewall opening. The API is restricted by firewall. Give the public IP addresses or ranges your requests will come from, so that they can be allowed.
  3. API token. The Brønnøysund Register Centre creates an API token for your QTSP with the agreed scopes.
  4. Explore and test (optional). For convenience, a Swagger UI is provided at https://auth-source-api.app-ppe.brreg.no/api/swagger.

When the API moves to OAuth 2.0, the static token is replaced by client registration with an authorization server. Onboarded QTSPs will be told in good time.

Endpoints

Paths are relative to the base URL.

MethodPathScopeDescription
POST/verifyverifyVerify attributes of a legal person (I2). The client sends the values it holds and gets a result per attribute.
POST/retrieveretrieveRetrieve attributes of a legal person (I3). The client names the attributes and gets the values from the register.

Request headers (draft)

X-API-Key
The API token issued to your QTSP at onboarding. Each token is registered with the scopes verify and/or retrieve.
X-Subject-Legal-Person-Id
The company the request is about: an organisation number (312546248) or an EUID (NOFOR.312546248).
Content-Type
application/json

Request bodies

  • /verify takes attributes, a list of attributeIdentifier and attributeValue pairs. Each attributeValue must be a JSON object.
  • /retrieve takes attributeIdentifiers, a non-empty list of {"attributeIdentifier": …}.
  • Both responses include provider, which identifies the Brønnøysund Register Centre as the authentic source.

Attributes

Identifiers are EBWV terms in the namespace https://w3id.org/ebwv#, used until the EU catalogue of attributes (Implementing Regulation (EU) 2025/1569, Art. 7) publishes official identifiers. Values are JSON objects keyed by the term, for example {"legalName": "EQUINOR ASA"}.

Values

  • legalIdentifier is a JSON-LD value object. In a verify request the plain EUID ("NOFOR.312546248") also matches.
  • legalStatus is inactive if the company is deleted, bankrupt, in liquidation or in compulsory dissolution, and active otherwise.
  • activity is the main industry code in SN2025, the Norwegian version of NACE Rev. 2.1, with five-digit subclasses such as 73.300. The scheme is named in the value because EBWV v0.1 has no type for SN2025.
  • Some attributes, such as contactPoint and subscribedCapital, are not registered for every company. A missing value gives Unknown in Verify and 404 in Retrieve.

Legal representatives

  • Active holders of the roles DAGL, LEDE, NEST, MEDL, INNH, DTSO, DTPR, KOMP, BEST, FFØR and REPR. DAGL (CEO) is written as the EBWV role CEO; other roles as https://data.brreg.no/enhetsregisteret/api/roller/rolletyper/{code}.
  • typeOfRepresentation comes only from the machine-readable signing combinations: Alone if the person is the only member of at least one combination, Jointly if they are in any other combination, and not set if they are in none. The free-text signatory rule is never interpreted.
  • Each representative has legalEntity, role and, where known, typeOfRepresentation. A person is a NaturalPerson with fullName, givenName, familyName and dateOfBirth; a company is a LegalPerson with legalName, legalIdentifier and legalForm.
  • The open data has no national identity numbers, so people are matched on full name and date of birth.

Verification results

Match
Every value in the request equals the value in the register. The response repeats the verified value.
MatchWithVariation
The values are equal only when case, whitespace, hyphens and diacritics are ignored. The response includes the register’s value, limited to the parts the request asked about.
NoMatch
The values differ.
Unknown
The register has no value, or the company is not registered.

A value matches when every property it states equals the register’s value. Properties left out are ignored, so you can verify part of an attribute, for example only the postCode of registeredAddress. In a list, each requested element must match an element in the register. An empty object never matches.

Errors

StatusMeaning
400Malformed request, or a missing or invalid subject header
